# 大清单迭代与持续验收

用于长期项目、多轮修改、阶段交付或询问整体进度。以当前版需求总账为恢复入口；不要求每轮翻查全部历史。普通小改可轻量记录，但仍继承有效要求。

## 四类记录及权威关系

- **大清单**保存本项目仍有效的目标、用途、约束与持续验收要点，用稳定ID组织父子关系。当前版本必须完整继承上一版有效内容。旧文件归档、工作重点改变、局部通过都不构成删除要求。
- **详细任务**记录为满足某要点而进行的研究、设计、实现或复核，关联一个或多个要点ID。任务结束只说明该任务的范围完成。
- **检查与反馈**保存所查成果版本、位置、方法、范围、结论和证据。助手技术复核、助手体验判断、独立复核与用户反馈分开；没有用户原话不能推定用户认可。
- **黑板**呈现当前总账版本、真实成果、当前重点、待依赖及下一步；引用总账，不再独立维护另一套完成状态。知识库存依据，经验库存有条件的方法，均不替代项目要求。

一个要点可以多次检查、复发、重开。某版通过后，该要点继续留在整体验收范围。避免为长期要点设置永久的“完成后隐藏”。

## 版本与继承

要求范围、含义或验收方式改变时更新大清单版本，记录父版及新增、修改、替代、取消的ID、理由与决定来源。普通任务拆分、检查和工作进度只新增对应记录，不另造一份竞争的大清单。

当前版保存完整有效内容；差异记录用于解释变化，不代替当前完整视图。保留ID，不重新编号；拆分/合并保留旧ID与继承映射。替代或取消须有明确范围、决定与依据，不能由“最近没有提到”推断。必要旧条目保留为失效记录，历史证据仍可查询。

首次整理既有项目时，从已知总需求、详细清单与后续有效决定建立基线，记录来源覆盖和迁移限制。对未核状态据实标注，不能把迁移完成写成设计验收通过。已存在的相同语义保留交叉映射，不靠删掉重复来源失去追溯。

## 每轮接续与回流

1. 首次接续或基线变化时恢复当前大清单、近期差异、活动成果身份和黑板重点；同会话已读取且版本未变时，复用上下文并定点检索相关ID、变化及最近证据，不重复全文输出。
2. 新反馈先定位影响的要点；无法归入时新增或调整要求，保留原话与含义。新要求追加或明确替代旧范围，不默认覆盖整体。
3. 实施前登记可能受影响的空间、人数、用途、门窗、路线、结构设备及表达版本，并关联要点ID。
4. 修改后检查直接影响及跨项依赖。旧证据只支持原版本；对未变部分可保留结论，但须有未受影响的说明。受影响或影响不明的要点标为待复核。
5. 保存实际成果、任务结果、检查记录与用户反馈；从总账生成当前视图，回写黑板。中断时至少保存当前版本、进行中任务与受影响未复核项。

## 验收与复发

日常修改只复核受影响要点与实际依赖；正式整体阶段交付逐项检查全部有效上级要求和验收要点。普通进度回报、单项文件交付和平台小改不自动升级为全项目验收。完整覆盖可复用仍适用的已有证据，不要求全项重算。每项可以是本版已复核、限定范围通过、发现问题、待证据、待用户评价或经说明沿用证据；不得用一张局部通过表代替整体覆盖。

新反馈否定旧效果、相关对象改变、用途/人数/运行工况改变、规范或来源改变、交付版本不一致，均触发重新判断。保留旧检查和失败原因，新增本版结论，不把旧通过报告改写为从未失败。已关闭的具体缺陷可因新证据重开，长期要点本来就持续有效。

技术、使用、体验与交付一致性分别给结论。用户评价不是所有客观技术检查的前置审批；助手技术通过也不替代用户对体验的判断。没有充分覆盖和证据，不能声明整栋成熟完成。

## 最小机器记录

可用现有数据库、JSON或等价表格，不强制安装新平台。单一权威源与可读视图必须可核对。一个轻量JSON约定：

- `version / parentVersion / changes`：当前完整版本、上一版及差异。
- `sources[{id,path,scope}]`：原始要求、决定和依据入口。
- `requirements[{id,parent,title,statement,acceptance,sources,tags,lifecycle}]`：持续要点；`lifecycle`为`active/superseded/retired`，后两者附理由和决定来源。可用`related`表达跨项关系。
- `artifacts[{id,path,sha256,role}]`：实际版本；新旧网页、RVT等分别标识，不把同名视为同版。
- `tasks[{id,requirementIds,status,...}]`：当次工作，与长期要点分离。
- `reviews[{id,requirementIds,artifactIds,artifactHashes,kind,verdict,scope,evidence,...}]`：版本化检查；`artifactHashes`保存实际所查内容身份，历史记录保留原貌；纠正或解决以新记录的`resolves`及理由指向旧ID。`kind`区分`assistant-technical/assistant-experience/independent/user-feedback`。用户否定不由助手通过记录消解。
- `sourceCoverage[{sourceId,requirementIds,scope,limitations}]`：声明基线纳入了哪些范围；完整性仍须实际读原资料核对。
- `pendingImpacts[{requirementIds,reason,...}]`：变更后未复核的影响。

路径相对于总账文件；快照与当前版保持相同解析根。检查器可运行`python scripts/check_requirements.py --ledger <current.json> --previous <previous.json> --out <report.json> --render <current.md>`。首版省略`--previous`。它检查ID、继承、来源、父子关系、证据文件身份及声明一致性；不能判断需求是否正确、影响是否漏报、设计好坏或规范是否满足，也不常驻自动监控。下一轮仍须实际读取、登记与运行。

需要可读矩阵时可运行`python scripts/export_traceability.py --ledger <current.json> --previous <baseline.json> --profiles <verification-profiles.json> --out <traceability.json> --html <matrix.html>`。方法映射可省略，提供时须与当前需求版本匹配。输出是只读派生，记录关联和检查声明，不执行验收闸门或计算设计完成率；具体核验边界见[verification.md](verification.md)。
